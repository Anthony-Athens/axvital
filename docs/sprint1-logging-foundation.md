# Sprint 1: logging foundation completion report

1. **Existing architecture.** Quick Log lives in `app/checkin/page.tsx`, also used by Today. Its payload builder writes legacy `health_events` with local `event_date`/`event_time`, free-text tags and optional type-specific fields. `lib/types.ts` defines `HealthEvent`, `HealthEventRow` and `HealthEventType`; recap/insight modules also have narrower read projections. The browser uses the authenticated public Supabase client; `lib/checkins/persistence.ts` already establishes the shared domain-function pattern. Server route clients are separate; no admin client is used here.

   The two application health-event insert sites found were Quick Log and development-only demo generation in `app/profile/page.tsx`. The profile page also deletes tagged demo events. `scripts/prelaunch-rls-qa.mjs` inserts synthetic security-test records. No other production health-event creator was found. Daily check-ins use `daily_checkins`. Food Quick Log redirects to nutrition: `nutrition_entries`, `nutrition_entry_items`, `foods`, `food_servings`, `user_foods`, `user_food_preferences`, `saved_meals`, `saved_meal_items`, and nutrition targets already exist. Food/meal logging uses transactional RPCs; custom foods use domain-managed inserts. Symptoms redirect to `user_symptom_events`, with `user_symptoms`, `symptom_event_conditions`, symptom/condition catalogs and user conditions. Their domain layer manages those writes. Existing food-classification assertions and immutable nutrition evidence support experiments; they are separate from taxonomy membership.

   Baseline health-event CREATE TABLE/permissive owner policies are absent from the repository. The existing hardening migration enables RLS and adds `sprint12_owner_guard`, a restrictive owner policy for every operation. Existing nutrition and symptom tables have owner/link policies; global foods/categories have authenticated, active-only read policies. Security tests use an explicitly synthetic baseline plus the repository migrations; they cannot certify a deployed schema.

2. **Design.** `lib/health-events/ingestion.ts` exposes `ingestHealthEvent` and `ingestHealthEvents`. It validates the entire input, allows only known payload columns, preserves values, verifies the authenticated owner, and issues one insert. It follows the existing browser-compatible domain pattern; client validation is not a security boundary. PostgreSQL RLS remains authoritative. Errors expose stable `INVALID_EVENT`, `AUTH_REQUIRED`, and `PERSISTENCE_FAILED` codes without payload/provider details. There is no service-role credential or new API endpoint. `input_method` describes the entry channel, leaving provider identity independent for future work.

3. **Migration.** `supabase/migrations/202609240001_logging_foundation.sql` is transactional and additive. Apply it before deploying the application change. It creates no replacement catalog or health-event table and changes no existing foreign keys. Existing events resolve to `manual` through a non-null constant default. Generated food keys backfill from existing names. Category and legacy alias/map seeding is idempotent. Existing IDs/display names/legacy categories/aliases remain intact. The optional rollback in `supabase/rollback/202609240001_logging_foundation_rollback.sql` removes the new structures only; export new metadata and roll back application code first. It intentionally retains seeded categories that may be referenced, and retains the safer catalog write grants.

4. **Schema additions.** `health_events.input_method` is constrained text: `manual`, `voice`, `integration`, `import`, `system`. Existing `foods` gains indexed, generated `normalized_name`; its existing name/description/activity/timestamps are reused. New `food_aliases` has a UUID key, cascading food FK, display alias, generated normalized alias, creation time, and uniqueness per `(food_id, normalized_alias)`. Ambiguous aliases across different foods are valid and must be resolved explicitly in a later sprint. Food names are deliberately not unique because brand/preparation identities can share names. New `food_category_map` has a composite primary key, cascading FKs, creation time and reverse category index. Existing `food_categories` is reused. Seeds cover the requested categories, retaining established `fruits` and `oils-fats` slugs instead of introducing synonymous `fruit`/`fats_oils` rows. Existing combined categories remain unchanged.

5. **Access model.** Health-event policies are unchanged. Authenticated users can SELECT aliases for active visible foods and category links for active visible foods/categories. Anonymous users have no privileges on either new table. Neither role can INSERT, UPDATE or DELETE either new table: grants are revoked and no write policies exist. Trusted service-role catalog maintenance has access to the new tables. Existing food/category read policies remain; possible default INSERT/UPDATE/DELETE grants for public/anonymous/authenticated roles are explicitly revoked. No health-data access is expanded.

6. **Files changed.** Modified `app/checkin/page.tsx` and `lib/types.ts`. Added `lib/health-events/ingestion.ts`, `lib/health-events/ingestion.test.ts`, `lib/health-events/quick-log.test.ts`, `lib/nutrition/normalization.ts`, `lib/nutrition/taxonomy.test.ts`, the migration, its optional rollback, and this report.

7. **Quick Log migration.** Fluid, Supplement, Exercise, Medication and Note now use the canonical single-event function. The existing payload builder, UI, timestamp handling, tags, success text, activation call, timeline refresh, form reset and failure draft retention stay in place. Food and Symptom retain their existing dedicated routes/storage. The existing catch handles standardized ingestion failures. Development demo generation and security fixtures are intentionally unchanged and receive the database's manual default.

8. **Atomicity.** All health events in a batch are validated before persistence and sent as one PostgREST INSERT, with no chunking or per-row requests. A database constraint/RLS failure aborts the entire statement. Empty/invalid/mixed-owner batches write nothing. A transport failure raises `PERSISTENCE_FAILED` without automatic retry; the server may have committed before the response was lost. This is atomic database persistence, not an exactly-once delivery guarantee. Existing UI activation/refresh occurs after persistence and is not part of that transaction. Batches do not span the independent nutrition or symptom domains.

9. **Tests added.** Nine tests cover default/explicit channels, all seven legacy event types, single/batch persistence, validation, authentication/ownership, payload/timestamp/tag preservation, returned/thrown persistence failures, and no retries. The rendered JSDOM Quick Log regression exercises all five migrated paths, failure retention, success/reset, tags, timeline refresh, sign-out and Food/Symptom routing. PostgreSQL/PGlite tests execute the real migration chain and new migration against the synthetic baseline, checking old-data/policy preservation, normalized keys, alias uniqueness, invalid FKs, category relationships, idempotent seeds, permissions/RLS, batch rollback on constraint/ownership failure, cascades, and rollback preservation. Normalization tests compare TypeScript and SQL output. Normalization deliberately folds ASCII case and ASCII whitespace only, preserving punctuation/diacritics; it is locale-independent and does not merge semantic variants.

The expanded five-path rendered regression was also rerun independently and passed. `npm run typecheck`: passed. `npm run lint`: passed. `npm run build`: passed; all 74 static pages generated. `git diff --check`: passed. Initial sandboxed esbuild tests failed on directory-access restrictions; the full suite passed outside that restriction. Existing Node module-type warnings remain. No deployed database migration or live Supabase/browser session was performed.

11. **Unchanged scope.** Existing nutrition/macronutrient data, food searches (`common_aliases`), primary `category_id`, classifications/evidence, timeline queries, check-ins, workouts, habits, protocols, experiments, conditions, pricing and analytics behavior are unchanged. No microphone, speech-to-text, AI/OpenAI call, parsing, voice UI, ingredient decomposition, food components, new nutrition dataset, barcode or restaurant integration was added.

12. **Deployment and Sprint 2.** Validate the migration on a staging copy with actual baseline policies/grants before production. Generated stored keys require a catalog table rewrite/lock; schedule migration accordingly. Legacy alias/category fields are backfilled once into the new foundation and remain the current UI's source; there is no ongoing dual-write synchronization. Before catalog editing or AI lookup starts using these tables, select one authoring source and define reconciliation, alias ambiguity, multilingual normalization, integration-provider provenance and idempotency/retry policy. Taxonomy membership must not silently become experiment classification evidence. Future multi-domain logging will need a separate transaction design if it includes structured nutrition/symptom records.
