# Voice nutrition quantity fix — validation report

Validated locally on September 25, 2026. No deployment, live OpenAI call, or physical-device recording was performed.

1. **Preserved work.** Continued the existing uncommitted schema, parser, prompt, catalog-enrichment and review changes. Preserved the existing Sprint 4 transaction/snapshot architecture and the unrelated user change in `supabase/.temp/cli-latest`.

2. **Root causes.** The original extraction contract had only textual `amount`; numeric quantity could exist solely in `title`. Canonical matching then received quantity-prefixed identities. The fallback recognized only a single number token immediately before the name, missing measurement units and `of`. Fractions such as `half a cup` and `one and a half cups` produced incorrect units. Review name edits reused the previous amount; structured edits did not update the amount text used for rematching. Serving selection could display an arbitrary default even when no safe conversion existed. Bare drink ounces were interpreted as mass, although the intended dimension was ambiguous.

3. **Three eggs trace.** Reproduced before: a schema-valid title `three eggs` with null amount reached matching unchanged, producing a provisional food and null quantity. After: grounded extraction repairs omitted quantity fields, returns identity `eggs`, quantity `3`, unit `each`; catalog enrichment selects the canonical `egg` food and its `1 large` / `1 each` serving. Review preserves `3 each`; persistence receives that serving ID and multiplier `3`. The database snapshot contains 216 kcal, 18.9 g protein, 1.2 g carbohydrate and 14.4 g fat (display rounding). A model response already containing `amount: three eggs` could work before; the defect depended on output shape.

4. **Chicken trace.** Before: quantity-prefixed chicken labels could miss matching, and a clean `chicken breast` title with null amount failed to recover `six ounces of chicken breast` from the source. After: both `6 oz chicken breast` and `six ounces of chicken breast` yield identity `chicken breast`, quantity `6`, unit `oz`. The canonical `chicken-breast-cooked` food has a stored 4 oz serving; the normalized multiplier is `1.5`. Snapshot: 280.5 kcal, 52.5 g protein, 0 g carbohydrate, 6 g fat. Six ounces is not six database servings.

5. **Review state.** UI tests verify initial quantity and macros; changing 3 eggs to 2 changes the preview from 216 to 144 kcal and the final multiplier to 2. Unit edits update both structured values and amount text. Numeric edits remove an obsolete quantity prefix from the display identity. Name changes clear the old food ID, components, amount and serving; a new quantity-prefixed name is reparsed. Removing a candidate removes its persistence row. Failed saves retain edited quantity/unit, and retries send identical rows. Existing component/exclusion review tests still pass.

6. **Canonical lookup.** Quantity and known measurement prefixes are removed before serving-backed catalog matching, including the rematch endpoint and inference fallback. Explicit ingredients/exclusions remain in source context. Conflicting extracted quantity/unit values are rejected; numbers belonging to another food cannot become this food's intake.

7. **Canonical parity.** Migration-backed tests resolve all representative foods to existing catalog IDs, comparing actual IDs rather than hardcoded UUIDs. Eggs, chicken and yogurt use the same food and serving IDs passed to manual logging. No catalog expansion or alternate food store was introduced.

8. **Serving parity.** Counts use `each` only if that food has a compatible stored item serving. Slices use slice servings. Direct unit matches take precedence; supported mass conversions use stored gram equivalents and volume conversions remain within the volume dimension. No arbitrary default serving is selected. Manual logging accepts a selected serving and its multiplier; voice normalization supplies that same representation. Both previews use existing `scaleNutrition`; both database paths use the existing shared snapshot writer. No new macro calculator or persistence migration was added.

9. **Macro parity.** Tests compare complete persisted calorie/protein/carbohydrate/fat snapshots, canonical IDs, serving IDs and multipliers against manual RPC writes for eggs, chicken, yogurt, oatmeal and rice. Greek yogurt uses 1 cup / multiplier 1 / 130 kcal. Half a cup of oatmeal uses multiplier 0.5 / 83 kcal. One and a half cups of rice uses multiplier 1.5 / 307.5 kcal. Macros come from stored servings, never model output. The final client payload contains serving ID, multiplier and stated amount, not authoritative nutrient values. Nutrition source metadata is `voice`; nonfood events retain `input_method: voice`.

10. **Intentionally incomplete.** Missing quantities, unsupported units, unsafe count mappings, unresolved foods and foods without nutrition servings remain review-required. Pepperoni pizza resolves but has no stored serving in the migration catalog, so two slices cannot acquire fabricated macros. `I drank 12 ounces of milk` retains quantity 12 with an unresolved unit; the user must choose weight or fluid ounces. Explicit `fluid ounces` is supported. Modified recipes still require reference-nutrition confirmation. Users may explicitly save incomplete entries without macros. Parsing is bounded, not a universal natural-language quantity interpreter.

11. **Files changed.** Production: `lib/voice/schema.ts`, `lib/voice/provider.ts`, `lib/nutrition/voice-nutrition.ts`, `lib/nutrition/food-service.ts`, `app/api/nutrition/resolve/route.ts`, `components/checkin/VoiceLogDialog.tsx`, `components/checkin/VoiceNutritionReview.tsx`. Tests: `lib/voice/schema.test.ts`, `lib/voice/provider.test.ts`, `lib/voice/ui.test.ts`, new `lib/nutrition/voice-quantity.test.ts` and `lib/nutrition/voice-quantity-database.test.ts`. This report is the only documentation addition.

12. **Regression coverage.** All seven requested parsing examples, numeric and word ounces with/without `of`, singular/plural units, count foods, slices of bread, unsupported bowls, missing amounts, ambiguous drink ounces, contradictory model output, review edits/removal/retry, canonical matching, persisted macro parity and duplicate-safe RPC retries. A mixed extraction/enrichment/persistence test verifies two eggs (144 kcal), 5 grams of creatine and a knee symptom; only the latter two become health events. Existing transaction tests verify rollback and changed-retry rejection. Structured diagnostics are test-level assertions; no user food details or transcripts were added to production logs.

13. **Validation.** Full suite: 682 passed, zero failed. Subsequent focused checks for the final review, rematch/prompt, parser and mixed database additions passed. Final TypeScript, ESLint, production build and whitespace checks passed. UI bundling initially failed with Windows sandbox `Access is denied`; the approved rerun outside the sandbox passed. No tests were weakened. The PGlite harness uses a documented synthetic baseline for original tables whose CREATE TABLE statements are absent from the repository, followed by the real repository migrations; it does not verify a deployed Supabase schema.

14. **Evidence boundary.** These are deterministic fixture, UI-harness and local database results. Audio transcription and actual model extraction in production were not observed. Provider behavior was tested with mocked responses. No live OpenAI request, microphone/device session, production database test or deployment was performed, so this report does not claim verified production correctness.

The extraction contract follows the documented strict structured-output requirements: every field is required, unavailable values use nullable types, and additional properties are forbidden. Reference: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
