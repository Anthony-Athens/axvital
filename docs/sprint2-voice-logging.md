# Sprint 2 completion report

1. **Architecture reused.** Sprint 1's `ingestHealthEvent`, `ingestHealthEvents`, canonical `HealthEventInput`/`HealthEventType`, ownership check, RLS, atomic batch insert and `input_method` are retained. Its deterministic validator is now exported for reuse before review and persistence. Today uses `app/checkin/page.tsx`; Voice Log sits beside the existing manual Quick Log buttons. The new sheet reuses `useSheetDialog` for focus trapping/restoration, Escape dismissal, scroll locking and mobile visual-viewport/keyboard handling. Server auth uses the existing cookie-based Supabase client, `guardWithClient`, `ApiError`, and database API budgets. Analytics use `trackProduct` and the existing property-reconstruction allowlist. There was no existing OpenAI integration or SDK dependency.

2. **Workflow.** Open Voice Log → Start recording → explicitly grant permission → Stop (or automatic 75-second stop) → upload/transcribe/extract/validate → inspect editable cards → Confirm and save events. Cancel is available during permission, recording, processing and review. Recording/processing never writes health records. The microphone is released before waiting for processing. Manual buttons, payloads and behavior remain intact.

3. **Files.** Modified `app/checkin/page.tsx`, `app/privacy/page.tsx`, `lib/api/validation.ts`, `lib/health-events/ingestion.ts`, `lib/telemetry/policy.ts`, and `.env.example`. Added `components/checkin/VoiceLogDialog.tsx`; `app/api/voice-log/parse/route.ts`; `lib/voice/{schema,recording,errors,api,provider}.ts`; five voice test files (`schema`, `recording`, `api`, `provider`, `ui`); `supabase/migrations/202609240002_voice_processing_budget.sql`; and this report.

4. **API.** `POST /api/voice-log/parse` is a Node route with a 90-second execution allowance. The existing guard authenticates first, requires a same-origin POST with multipart data, rejects unexpected query parameters, and consumes a shared per-account database budget. Binary upload validation bounds the stream, validates field names/duplicates, MIME/container signatures, timezone, recording age and claimed duration. Actual decoded duration is checked after transcription, before extraction. Responses have `Cache-Control: private, no-store`. There is no voice-specific persistence endpoint.

5. **Dependencies.** None added. Native server `fetch`, `FormData`, `File`, and `AbortSignal` call the provider. Existing esbuild, JSDOM and PGlite support testing. The project already uses these Node/Web APIs. No raw-audio decoder or storage service was introduced.

6. **Configuration and deployment.** Set server-only `OPENAI_API_KEY`. Optional `OPENAI_VOICE_EXTRACTION_MODEL` defaults to `gpt-4.1-mini`; overrides must support the Responses API and strict JSON-schema output. Never prefix the key with `NEXT_PUBLIC_`. Missing key produces `VOICE_UNAVAILABLE`, without calling OpenAI. Apply Sprint 1's logging migration and `202609240002_voice_processing_budget.sql` before deploying. The latter adds three parse requests per account per minute to the existing budget function, preserving existing routes and privileges; no health-data RLS changes or new tables are required. It fails closed if its expected function definition is absent. Nothing was deployed or applied to a remote database during implementation.

7. **Transcription.** OpenAI `whisper-1` through `/v1/audio/transcriptions`, using `verbose_json` and temperature zero. This choice supplies decoded duration and available no-speech metadata, while the extraction layer receives plain transcript text. Empty text and segments uniformly above the configured no-speech threshold are rejected. Transcription timeouts/failures return fixed error codes. The format is documented in [OpenAI file transcription](https://developers.openai.com/api/docs/guides/speech-to-text).

8. **Extraction.** OpenAI `gpt-4.1-mini` through `/v1/responses`, with `store: false`, a strict named JSON schema, no tools, bounded output and a 30-second timeout. The prompt treats transcript text as data, requires verbatim source/title fragments, rejects hypothetical/future instructions, and prohibits diagnoses, advice, invented doses and nutrient estimates. Refusal, incomplete output, malformed JSON and invalid candidates fail closed. See [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) and [GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini).

9. **Candidate schema.** The closed extraction envelope is `{events: [...]}` with at most 12 items. Fields are canonical `event_type`, `title`, `amount`, `dose_amount`, `dose_unit`, `duration_minutes`, `distance`, `distance_unit`, `intensity`, `severity`, `notes`, plus transient `time_expression` and `source_fragment`. All optional model fields are explicitly nullable. Validation requires source/title/context to occur in the transcript, numbers to have literal evidence, quantities to match their stated units, and fields to match the event category. No calories/macronutrients, owner IDs or arbitrary model fields are accepted. The response contains canonical event drafts plus source fragments, time notices and `requires_review: true`; it does not return internal reasoning or the full transcript. No competing storage model was added.

10. **Review and time.** Users can change type/name/date/time, relevant quantity/unit/duration/distance/intensity/severity, notes and tags; remove individual candidates; or cancel everything. Changing type clears incompatible structured fields. Every card exposes its timestamp and expandable source fragment. Time resolution uses the browser's IANA timezone and validated recording-start timestamp. Explicit AM/PM/24-hour times and qualified morning/evening times are resolved; noon/midnight and yesterday/last-night date shifts are supported. Approximate morning/afternoon/lunch/tonight phrases retain the reference clock with a clear review notice, rather than inventing an hour. Confidence scores are not shown.

11. **Persistence.** Only the explicit confirmation handler invokes `reviewedInputs` followed by Sprint 1 `ingestHealthEvents`. It supplies the authenticated owner, forces `input_method = voice`, validates again, derives the existing compatibility fields (`dose`, `duration`, `supplement_name`, etc.), and saves only the remaining reviewed events. Source fragments/time notices are not persisted. The existing single-statement batch/RLS behavior applies. Successful saves refresh the Today timeline. Failures preserve drafts. Because Sprint 1 cannot distinguish a rejected insert from an uncertain transport result, retry after `PERSISTENCE_FAILED` is disabled until the user confirms they checked the timeline. No automatic retries or exactly-once guarantees are claimed.

12. **Privacy and observability.** Raw audio and transcripts are held in memory only; no bucket, transcript table, localStorage draft or recording history is created. The provider module is `server-only`. Browser production assets were checked for the OpenAI key variable and endpoint code; neither was present. The guard logs fixed route/status/category only for server failures. No raw errors, recordings, transcript/source text or health values are forwarded to ordinary logs or telemetry. Nine behavioral voice events use the existing allowlist and empty reconstructed payloads. OpenAI can retain data according to the account's applicable provider settings; `store: false` is not a promise of zero provider retention. The recording screen and privacy page disclose the processing.

13. **Limits.** 75-second client auto-stop; 3,000,000-byte audio limit; 8,192 additional bytes for multipart overhead; 10-second upload-read deadline; recording timestamp within 10 minutes of server time; three processing attempts per account per minute; 30-second deadlines for each provider request; 80-second browser processing timeout; 12 candidates. Claimed and provider-decoded duration allow two seconds of encoder tolerance. File duration is verified after transcription, so rate/byte limits are the pre-provider resource controls. Cancel/unmount/backgrounding during capture releases tracks and invalidates pending work, including late permission resolution.

14. **Browser assumptions.** HTTPS (or a browser-recognized secure localhost), `getUserMedia`, `MediaRecorder`, supported WebM/Opus or MP4 audio, and modern browser Web APIs are required. MIME support is checked at runtime; unsupported browsers show an actionable fallback to manual logging. MP4 is included for browsers that cannot record WebM. Tests mock media/permissions and render in JSDOM; no physical microphone, iOS/Android device, actual Safari/Chrome recording, native permission UI, or real visual-viewport geometry was verified. Validate those on staging before release.

15. **Tests added.** Fourteen tests cover representative mixed food/fluid/supplement utterances; null missing doses/durations; symptom text without generated diagnosis; closed schema and grounding; relative times/timezones; edited/removed candidate conversion; analytics payload stripping; request auth/origin/rate/size/type/duration; PostgreSQL budget behavior; provider configuration, request shape, silence, refusals and failures; recorder limits/cancel/late permission/cleanup; and rendered UI state transitions, edit/remove/confirm, uncertain-save acknowledgement, background interruption and sign-out. Responses and transcripts are fixtures, not evidence of live model accuracy. No test calls live AI.

16. **Validation.** Full `npm test`: 653 passed, zero failed. After final fixes, the 21 voice and Sprint 1 ingestion/manual Quick Log tests also passed. Final `npm run typecheck`, `npm run lint`, `npm run build` and `git diff --check` all passed; the build generated 75 static pages. ESLint initially identified a React ref update during render and a test naming issue; both were corrected. Initial sandboxed esbuild tests hit directory access restrictions; they passed outside that restriction. Existing Node module-type warnings remain. No tests were weakened. One typecheck overlapped Next's generated-type rewrite; it passed when rerun after the build.

17. **Known limits.** Food and Symptom voice events deliberately use legacy `health_events`, as requested, and therefore populate the activity timeline rather than structured nutrition/symptom trackers; this is disclosed during review. Exact-once save idempotency is absent. Temporal grammar and number-word support are conservative and mainly English; ambiguous or unsupported phrasing may need manual correction/re-recording. Prompting, quoting and deterministic checks reduce fabricated data but cannot establish semantic truth or guarantee model accuracy. No live-provider smoke test, staging migration, physical-device recording or human visual QA was performed. The existing food taxonomy is not used to infer ingredients, nutrition or experiment evidence.

18. **Sprint 3.** Prioritize real-device/permission/codec tests and a synthetic-data live-provider evaluation, then evaluate transaction idempotency, user-level daily/global spend controls, supported multilingual/time-expression expansion, and whether structured nutrition/symptom domains should join a future multi-domain transaction. Keep ingredient decomposition, realtime conversation, integrations and automatic writes out of this release. Apply and verify both required migrations and provider configuration on staging first.
