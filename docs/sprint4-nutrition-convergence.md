# Sprint 4 — voice and Nutrition Tracker convergence

1. **Nutrition Tracker audit.** See the pre-implementation findings in `sprint4-nutrition-audit.md`. Global nutrition definitions live in `foods` and `food_servings`; owner-private definitions live in `user_foods`. Intake uses `nutrition_entries` and `nutrition_entry_items`. Items snapshot serving identity, quantity multiplier, grams and calories/protein/carbohydrate/fat/fiber/sugar/sodium/caffeine/alcohol. Manual search covers names, brands and common aliases. Custom foods require user-supplied nutrition. Manual preview uses `scaleNutrition`; authoritative snapshots are written in PostgreSQL. Entry edits cover time/meal/notes; deletion is soft deletion. The tracker currently displays today's entries, while Activity supports its existing date ranges.

2. **Sprint 1–3 audit.** Canonical health ingestion, verbatim-grounded voice extraction, normalized aliases, many-to-many categories, global components, event-specific components/exclusions, provenance, category derivation and bounded optional AI matching already existed. Voice food previously persisted as a generic health event with food metadata. All this metadata remains available; the authoritative intake anchor changes for new voice foods.

3. **Catalog conclusion.** There was **one global catalog with incomplete integration**, not two global catalogs. Sprint 3 extended the same `foods` table. Private custom foods remain intentionally separate. Generic Chicken/Bread and more specific cooked breast/whole-wheat bread are not proven duplicates; they are not merged or assigned guessed nutrition.

4. **Final source of truth.** New voice food and fluid candidates persist in `nutrition_entries` / `nutrition_entry_items`. `source_type='voice'` is the existing provenance field extended with a voice value; manual stays `manual`. Nutrient values come only from catalog/private-food serving records. Resolved voice and manual entry items have identical structure and calculations. Unresolved food is an explicitly reviewed `nutrition_status='incomplete'` entry with no fabricated item/nutrients.

5. **Services/tables.** `log_food_atomic` remains the manual and resolved-voice nutrition API. Its snapshot logic is factored into `append_nutrition_food`, also used to complete unresolved intake. `ingest_voice_nutrition` coordinates a mixed recording. TypeScript `logVoiceNutrition` validates/reviews the draft and sends only food IDs, serving IDs and multipliers—not client macro values. `complete_nutrition_entry` completes an owned incomplete entry in place. Existing non-food health-event ingestion remains intact. `health_event_foods` retains its compatibility name but now supports either a legacy health-event anchor or a nutrition-entry anchor, never both. Its existing component child table is reused.

6. **Migration.** `202609250001_voice_nutrition_convergence.sql` extends nutrition provenance/status/stated amount/tags, adds the nullable nutrition anchor with unique/composite ownership constraints, adds the invoker nutrition category view and atomic RPCs, and creates private request receipts. It extends account schema inventory and adds egg aliases idempotently. No tables or history are recreated; no nutrient/serving records are invented. The old source-type constraint is replaced with an expanded list retaining every prior value.

7. **Convergence/mapping.** Matching first searches serving-backed canonical IDs in the same catalog, preserving exact → alias → normalized → conservative fuzzy ordering. It then uses the existing taxonomy identity if no serving-backed match is safe, followed by the existing bounded AI/provisional path. Component enrichment uses the full shared catalog. No automatic global food creation, speculative ingredient substitution or destructive merge occurs. Existing historical Sprint 3 health events and metadata are retained as legacy read-only activity. They are not copied into Nutrition Tracker because their serving quantities/timezone cannot safely be inferred; therefore no historical duplicate activities are introduced. Future explicit backfill would require user-reviewed mappings/servings/timezones.

8. **Macros.** Preview reuses `scaleNutrition`. Persistence reloads the selected serving/private food inside PostgreSQL and multiplies every existing nutrient field. A direct database test compares manual and voice snapshots for three eggs: both use the existing Egg ID, serving ID, multiplier 3 and 216 stored-reference calories. Protein/carbs/fat match exactly too. Numbers are rounded only for display. Unknown values remain unknown. Tracker totals reuse `totalKnownNutrition` and visibly disclose incomplete data; incomplete entries never masquerade as zero-calorie food.

9. **Serving conversion.** Deterministic parsing structures the model's verbatim amount text, with a bounded adjacent-food fallback when amount is missing. Examples: three eggs → 3 each; six ounces → 6 oz; one cup → 1 cup. Missing quantities stay null; unsupported units remain unresolved. Same-unit quantity divides by the stored serving quantity (6 oz / 4 oz = 1.5). Weight conversions use the serving's gram equivalent when available, otherwise compatible mass units. Compatible US volume units convert by fixed ratios. No mass-to-volume density is invented. A default serving can be selected for review, but a missing quantity is never silently filled. Consumed timestamps use the reviewed browser-local date/time, matching manual datetime-local behavior; nonexistent local times are rejected.

10. **Composites.** Existing components, provenance and exclusions persist under the nutrition entry. A known reference serving can supply macros; taxonomy-only pizza/sandwich/burger components cannot. Changes/exclusions require explicit confirmation that the reference nutrition applies, or save as incomplete. Excluding cheese never silently subtracts an assumed cheese quantity. There is no AI recipe-calorie estimator and no new quantified-recipe editor. The existing saved-meal/reuse infrastructure is preserved; voice recipe assembly from component quantities is deferred. Users can complete incomplete intake using a known serving or a private custom food whose nutrition they supply.

11. **Manual/voice parity.** Both resolved paths call the same snapshot writer through `log_food_atomic`. The original manual API signature, serving UI and custom-food flow remain compatible. Voice review adds serving selection, quantity/unit editing, meal context, rounded macro preview and explicit incomplete-save acknowledgement. Changing a food name invalidates stale serving metadata; changing amount reparses quantity. Existing ingredient review remains optional. The extraction schema stays strict: names, amount/unit text, explicit brand/product wording, meal context, ingredients, exclusions and time are grounded in the utterance, and deterministic serving resolution follows. AI never supplies nutrition numbers.

12. **Mixed saves/retries.** The browser validates every candidate before writing. Food/fluid rows use nutrition persistence; supplements, symptoms, exercise, medication and notes use the existing canonical health RPC inside the same PostgreSQL transaction. A failure anywhere rolls back entries, items, components, non-food events and the request receipt. The same owner/request UUID and identical payload is idempotent; changed content under a committed request ID raises `VOICE_RETRY_CHANGED`. The UI retains drafts and the request ID after an uncertain failure and preserves the existing timeline-check acknowledgement. Non-food-only recordings retain their existing canonical ingestion path and retry behavior.

13. **Activity.** New voice foods create no generic food health event. Existing nutrition hydration yields exactly one activity per nutrition entry, just as for manual logging. Incomplete intake has an explicit incomplete subtitle and null macro metadata. Completing an entry retains its ID and original time/notes/component history rather than adding another visible log. Soft-deleted entries remain excluded from the timeline and the nutrition category view.

14. **RLS/security/privacy.** All RPCs use caller privileges. Snapshot writing checks ownership, visible active references, serving/food identity, owned active custom foods and finite positive quantity. Nutrition parent ownership and component ownership are enforced by RLS plus composite foreign keys. Global reference data remains read-only to ordinary users. Existing health-event policies and immutable nutrition evidence triggers are unchanged. Receipts are owner-scoped, insert/select-only for ordinary users, contain an opaque request UUID/hash, and cascade with account deletion. They are operational data excluded from account export; intake/component records remain exported. Voice/resolution endpoints retain authentication, same-origin checks and shared budgets. No service-role secret or food/quantity/nutrient/transcript payload is added to behavioral analytics.

16. **Tests.** Deterministic coverage includes manual/voice snapshot parity, exact/alias/normalized/fuzzy serving-backed resolution, ambiguity, same-catalog metadata fallback, unresolved food, quantity parsing/conversion, missing/unsupported units, known reference versus unquantified composites, edited macro preview, mixed event partitioning, complete transaction rollback, idempotent duplicate prevention, changed-payload rejection, owner isolation, export/deletion, in-place completion and immutable evidence. UI assertions retain exclusion provenance and uncertain-save recovery while asserting the new nutrition path. Timeline and totals tests verify one representation and explicit missing-data semantics. Original regression assertions remain, with old voice-food persistence expectations updated to the requested nutrition destination.

18. **Limitations.** The small curated catalog still leaves many foods without servings. Those require explicit incomplete-save review or manual custom nutrition. Component quantities are not collected for recipe summation. Serving conversion uses US volume definitions, not regional cup assumptions; unsupported units need correction. Browser-local timestamp handling has the same ambiguous-DST-time convention as manual logging. The existing tracker UI is today-focused; older incomplete entries remain stored/exportable, but a historical review queue is future work. Private custom foods can complete intake through the tracker; voice automatic matching currently targets the global catalog. Catalog-size limits and bounded AI fallback from Sprint 3 remain.

19. **Production risks/backfill.** Apply the new migration after Sprint 3 and before deploying these application changes. It checks the account schema and depends on the repository's prior function/constraint definitions. Validate those against staging because original baseline DDL is not in this repository. The migration does not guess historical timezone, quantities or macros, and does not rewrite prior voice records. No rollback SQL is supplied: removing nutrition anchors or the new source value after voice data exists could discard valid intake/history. Prefer a forward corrective migration after backup and staging verification.

20. **Sprint 5.** Add a historical incomplete-food review queue and stronger explicit food/product selection, including private custom foods. Consider reviewed recipe servings with real component quantities and immutable recipe versions. Evaluate safe user-assisted legacy import with timezone/serving review. Run staging RLS, concurrent retry and real-device voice/serving QA before expanding the catalog or linking nutrition intelligence to downstream analysis.
