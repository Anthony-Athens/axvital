# Sprint 4 pre-implementation audit

Conclusion: **A — one canonical `foods` catalog with incomplete integration.** Sprint 3 extended the same table already used by Nutrition Tracker. `user_foods` is the intentional owner-private custom-food model, not a second global catalog. Generic ingredients such as Chicken/Bread and specific foods such as Chicken Breast, Cooked/Whole Wheat Bread are not proven equivalents and must not be destructively merged.

Nutrition Tracker stores global serving definitions in `food_servings`, private custom definitions in `user_foods`, intake in `nutrition_entries`, and immutable consumption/serving/nutrient snapshots in `nutrition_entry_items`. Nutrients include calories, protein, carbohydrate, fat, fiber, sugar, sodium, caffeine and alcohol. Manual `logFood` calls the authenticated, security-invoker `log_food_atomic` RPC. It loads a serving or owned custom food and multiplies its stored values by the selected quantity. There is no existing general unit-conversion engine; the UI selects an existing serving and a multiplier. Unknown nutrient fields stay null. Daily totals sum snapshots; currently null values are coalesced to zero without an incomplete-data notice.

Manual search filters names, brands and `common_aliases`. Custom entry creates an owned `user_foods` record requiring at least one supplied nutrient value; it does not write the trusted catalog. NutritionHome previews with `scaleNutrition` and reads today's entries. `updateEntry` changes time/meal/notes; `deleteEntry` soft-deletes. Today/Activity already hydrates nutrition entries directly through `lib/timeline/sources/nutrition.ts` and links to the tracker. Generic health events are hydrated separately. The nutrition timeline currently displays zero totals for missing snapshots, which needs correction for unresolved voice entries.

Sprint 1–3 adds normalized aliases, many-to-many categories, global component edges, canonical matching, cautious AI fallback, and owner-specific `health_event_foods` / `health_event_food_components`. Exclusions, source and individual confirmation are retained. Voice candidates carry `event.food`; the reviewed batch currently calls health-event ingestion and therefore uses a generic health event as its primary food record. That is the persistence divergence to remove. Reference-only Sprint 3 foods intentionally have no invented servings/macros and are hidden from the serving-based manual picker.

RLS: shared active foods/categories/servings/aliases/components are authenticated-read-only; user foods and nutrition entries are owner scoped; item ownership follows the parent entry and private-food references are hardened. Health-event policies are independent. Browser calls use the authenticated client; trusted nutrient snapshot creation occurs inside PostgreSQL, not from AI values. Account export/deletion has a strict relationship inventory that must be extended with any new nutrition anchor.

Chosen design before implementation: retain canonical IDs and all historical rows; prioritize serving-backed foods during voice resolution; use `log_food_atomic` for both manual and resolved voice nutrition, wrapped by an atomic mixed-domain voice RPC. Extend existing component metadata with a nutrition-entry anchor rather than introducing another catalog or generic food event. Unresolved intake uses an explicitly reviewed incomplete nutrition entry with unknown macros. Existing legacy voice health events remain read-only history; no automatic conversion can safely invent their serving quantities or timezone. New voice foods create no generic food events, so existing nutrition timeline hydration produces one visible entry.
