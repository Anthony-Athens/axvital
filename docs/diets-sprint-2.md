# Diets — Sprint 2

Nutrition → Diets provides reusable drafts independently of experiments. Definitions can be incomplete, edited, archived and restored. Following captures a validated rule/schedule snapshot. Saving the reusable definition never rewrites enrolled history. Apply rules with an effective date to create another immutable version; historical changes require explicit acknowledgment. The latest revision wins when versions share an effective date. Stopping has an inclusive final date. Future enrollments can be cancelled without generating expected assessment dates. Stopped history still permits explicit dated corrections.

## Creating and following a diet

1. Open Nutrition → Diets → Create diet. Enter a name and optional instructions. Instructions are explanatory and never executed as rules.
2. Add food/category allow and exclude rules, or ingredient restrictions. Food choices use existing canonical foods and aliases. For a slow-carb-style example, choose appropriate proteins, legumes and vegetables; exclude appropriate grain/starch, fruit and dairy categories or individual bread, rice, pasta, potatoes and tortillas; allow water, plain coffee and unsweetened tea. Inspect the actual catalog categories rather than assuming a category proves ingredients absent.
3. Select illustrative or exhaustive policy. Illustrative lists permit resolved unlisted foods unless another rule excludes them. Exhaustive lists require a food/category allowance. A specific food rule overrides category rules; ingredient exclusions still apply. Duplicate/contradictory subjects and known equal-specificity category conflicts block activation. Later catalog conflicts produce Needs review.
4. Expand planned exception days. Select recurring weekdays and/or individual dates. Save draft at any stage. Expand Start following, choose start/optional end and timezone, then Save and follow diet.
5. Continue existing manual/voice logging. Select an elapsed date in Following and history. Inspect applicable rules, ingredient evidence and source references. Unknown ingredients stay Needs review; missing macros do not imply unknown ingredients or prove ingredients absent. Correct identities/classifications in the private review controls with provenance and explicit historical scope. These corrections do not change shared USDA/provided food provenance or nutrient snapshots.
6. Confirm all food and beverage logging. A zero-entry date also requires deliberate no-intake confirmation. Known violations remain Nonadherent even when logging is partial or other ingredients are unknown. Otherwise unresolved evidence wins over incompleteness; Adherent requires complete logging. Exceptions retain actual intake/reasons/completeness and are counted separately as Planned exception.
7. To change rules/schedule, edit the reusable definition, then use Manage effective rules to apply the shown plan from a date. Use the historical acknowledgment for retrospective changes. Archive unused definitions or stop following without deleting history.

## Sources and freshness

Daily source snapshots come from an owner-authorized PostgreSQL RPC: canonical nutrition entries/items, persisted logged components, canonical component library, existing legacy food/fluid health events, and private/shared reviewed classification evidence. Logged composite components replace the parent/item assessment; they are not added on top. Manual and voice persisted composites share this path. Library expansion has bounded depth and fails closed on unresolved/cyclic relationships. Unconfirmed AI/fuzzy identity stays reviewable. Private specificity is component/item, then logged anchor/event, then user food, then canonical-food correction, then reviewed shared evidence. Corrections at a broader scope explicitly affect prior matching intake.

Assessments are derived on every request, with no persisted adherence checkbox or stale assessment cache. Completeness is separate and is bound to a source fingerprint. Parent/item and additional beverage/component/evidence triggers invalidate affected confirmations, including both sides of moved logs. A retained previous fingerprint explains invalidation; confirmation requires the current fingerprint under the same owner lock as ingestion. Reviewed shared catalog changes also change the fingerprint conservatively. The UI clears old results while refreshing, displays errors without stale statuses, and refreshes on return/focus and explicit Refresh. Source changes in another tab require focus/refresh; there is no realtime subscription.

History shows up to 31 elapsed dates around the selected date. Select earlier dates to inspect earlier windows. Dates outside enrollment, future dates and cancelled enrollment dates have no assessment. No personal diet, enrollment or example was created.

## Sprint 3 interface

`lib/diets/service.ts` exports `readDietAssessment(client, enrollmentId, localDate)` returning `{ bundle, assessment }`. Owner validation is enforced by `read_diet_day_v1`; `read_diet_window_v1` supplies bounded historical snapshots. `Assessment` in `lib/diets/model.ts` is contract version 1: enrollment ID, immutable applicable rule-version ID, local date/timezone, calculated status, logging completeness, explicit no-intake, confirmation invalidation, exception, review/violation/allowed reasons with source/evidence references, fingerprint, calculation version `diet-v1`, and freshness `current`. The bundle includes enrollment and applicable plan/version. RPC failure is unavailable, never current. Sprint 3 can consume this interface; no diet factors, exposure analyses or protocol adherence checkbox were added.
